# The 6309 — how to run one before there is a core that is one

⚠ **A PLAN, NOT A DESIGN.** Asked 2026-09-21: *we want to optimise all our code
for the 6309; the machine will definitely be an HD6309E; is there a way to
simulate one before the Verilog model exists?* The answer is yes, the path runs
through the **host emulator and not through Verilator**, and the first step costs
an afternoon and is worth doing whatever else happens (§4.0).

Companion: `software/toolbox/docs/proportional-font.md` §8, which is where the question came from
and which is blocked by it.

⭐ **Items 1 and 2 need no new code at all — they need a make variable and a
model that can run it.** That is the shape of this whole document: the code is
already written, by other people, years ago, and what is missing is a machine to
run it on.

## 3. Why it needed a model before it could be switched on

A `CPU=6309` build on a 6809 model links, boots and **silently does the wrong
thing** — a `TFM` copies nothing, `F$Move` with it — because a 6809 decodes the
6309's opcodes as something else. §4.0 closed that (the 6809 model refuses them);
§4.1 is the model that runs them.

⚠ **And there is no off-the-shelf conformance suite.** `hardware/cpu/docs/plan.md` §6.1
already found this: SingleStepTests covers 6502/65816/68000/8088/Z80/SPC700 and
has **no 6809 or 6309 set**. Whatever validates a 6309 here has to be built.

⭐ **But most of it already was.** `hardware/cpu/sim/test/run.sh` is a
**generated differential exerciser**: `gen.py` (557 lines) emits self-contained
chunks that load every register an instruction depends on and then execute it,
under a pseudo-random interrupt schedule, and the harness compares **every
register at every instruction boundary and every write with its E cycle** between
`cpu6809.c` and `mc6809e.v` — plus `cycles.py`, which fails if the Verilog shows
any instruction length that is neither the datasheet's nor one of the documented
exceptions. **The machinery for validating a CPU model against another CPU model
is built, tested and in use.** What a 6309 needs is a second implementation to
point it at.

## 4. The plan

### 4.0 ⭐⭐ BUILT 2026-09-21 — the host emulator REFUSES a 6309 opcode

**The worst failure mode in the project is closed**: a 6309 instruction no longer
decodes as its 6809 ghost and runs on. It names itself and stops.

| | |
|---|---|
| ⭐ **`hardware/cpu/sim/test/hd6309.tab`** | **436 opcodes**, one line each: page, opcode, mnemonic, mode, length, **emulation-mode and native-mode cycles**, and whether the encoding is **6309-only**. Checked in, because the book it comes from is not |
| ⭐ **`hardware/cpu/sim/test/mk6309tab.py`** | derives it from **two independent sources** and fails on disagreement: encodings from **lwasm** (the assembler that actually produces this project's code) and lengths and cycles from **Appendix A of `The 6309 Book`**. `--from-tab` regenerates the C header from the checked-in table alone, for a machine with no PDF |
| ⭐ **`hardware/cpu/sim/hd6309ops.h`** | generated: a bitmap of the **168 encodings a 6809 model must refuse**, plus their names |
| ⭐ **`cpu6809.c`** | checks the **raw** opcode before `ghost[]` destroys the evidence, and calls `c->undef6309` — which by default prints the mnemonic, the address and the cycle, and aborts |
| ⭐ **`hardware/cpu/sim/test/refuse6309.c`** | a gate: drives **all 768 (page, opcode) pairs** and asserts 168 are refused *by name* and 598 run |

⭐ **The two-source rule earned itself three times in one afternoon**, and each
failure would have been invisible in a typed table:

1. ⛔ **The book's OCR invents opcodes.** `$1050 NEGW`, `$1057 ASRW` and
   `$1058 ASLW` were read out of the appendix's `---` rows by column bleed.
   **lwasm answers "Bad opcode" for all three while `COMW` and `LSRW` beside them
   assemble** — so they are dropped and counted. A fabricated entry in a refusal
   table is a **spurious trap on working 6809 code**.
2. ⛔ **`--6809` is the restrictive flag; omitting `--6309` is not 6809 mode.**
   lwasm's default accepts 6309 mnemonics, so the first classification pass called
   423 of 439 encodings "shared" and would have refused almost nothing.
3. ⛔ **A failure to ask is not a negative answer** — CLAUDE.md's eighth trap, in
   Python. A probe that neither assembler could build was being scored as
   "6309-only", which invented a refusal for **`CWAI`**, whose operand the book
   omits. Unresolved is now its own state and the count is printed.

⚠ **The exerciser is the one place that must NOT refuse.** `gen.py` runs with
`--undoc`, so it deliberately executes the ghost encodings — `$01`, `$02`, `$05`,
`$0B` and friends — because the whole point of that harness is that `cpu6809.c`
and `mc6809i.v` agree about them. `cpu_run.c` sets `undef6309` to a counter and
carries on; the machine emulator keeps the default.

⭐⭐ **AND THAT CONFLICT IS ITSELF A FINDING.** Those same bytes are
**OIM, AIM, EIM and TIM** on a 6309. `mc6809i.v`'s ghost decode — which
`cpu6809.c` faithfully models — says `$01` is `NEG`. **On the machine this project
is actually building, `$01` is `OIM`.** The two models agree with each other and
both differ from the CPU in the socket. Nothing executes those bytes today, so it
costs nothing today; it is a divergence-ledger entry waiting to be written, and it
is why the refusal is on by default in the machine and off only in the harness
that is deliberately testing the Verilog.

⛔ **Still owed: `mc6809e.v`'s wrapper in `machine3.v`.** The Verilog core has its
own ghost decode and no equivalent refusal, so `check:machine` would still run a
6309 opcode as something else. It matters less — that bench runs `boot.asm`, which
is 6809 by construction — but it is the same hole.

**Verified**: the full differential suite (`hardware/cpu/sim/test/run.sh`, 8 seeds × 3M cycles)
passes unchanged with the refusal in — every documented 6809 opcode identical on
both cores, 3.8 M instructions cycle-checked, and `demo_run`'s register trace still
byte-for-byte `refplayer`'s.

### 4.1 ⭐⭐ BUILT 2026-09-24 — `hd6309.c` is a complete HD6309E, held to an oracle

`hardware/cpu/sim/hd6309.c` is a **complete core**, not a layer: `cpu6809_step` hands it
the whole step when `is6309` is set, so none of `mc6809i.v`'s quirks (the ghost decode,
`SWI` at 20, `SEX` without flags) reach it, and the 6809 path is byte-identical to what
the Verilog differential has always run. Every encoding the 6309 defines, both modes,
native mode's stacking (W between DP and B), `FIRQ`'s entire-state bit, both traps at
`$FFF0`, the hidden M register, `TFM` with §4.3.1's decided semantics.

**What decides what**, in order of trust — and every departure from the first two is
marked `[silicon]` or `[XRoar]` at the line that makes it:

| | source | settles |
|---|---|---|
| 1 | **silicon**: hoglet67's (David Banks) logic-analyser work and Tim Lindner's fuzzing | the divides' overflow rules and operand-dependent timing, `MULD`'s, `DAA`'s 6309-only correction, `SEX` and `LDQ` leaving V, the M register |
| 2 | **The 6309 Book** and its **Addendum** (the indexed postbyte costs, both modes) | every instruction's semantics, native mode's stacking, `STQ` clearing V |
| 3 | **XRoar** | a mixed-size `TFR`/`EXG`, `CWAI`'s wake cycles — where the first two are silent |

**The cycle table is silicon's.** `test/hd6309.tab` stays the book's record; `test/hd6309.silicon`
lists the 29 places silicon corrects it — every prefixed inherent op (the book dropped the
prefix's cycle: `NEGD` is 3/2, not 2/1), `TIM` (4/5, not 6/7), `EIM` indexed, `SEXW`,
`ORCC`, `SYNC` — and `mk6309tab.py` applies them to `hd6309ops.h`. ⭐ **`oracle/checkcyc.py`
fetches hoglet67's decoder and requires all 436 opcodes in both modes, and both 256-entry
postbyte tables, to equal it.**

**The oracle is XRoar's HD6309** (`oracle/fetch-xroar.sh`), fetched at a pinned commit and
built into `hardware/cpu/build/` as a separate program — ⛔ GPL-3.0, never copied here.
`test/gen6309.py` writes programs of one chunk per instruction, every register loaded
first, control flow built rather than drawn; `cmp6309.py` requires every register at every
boundary and every write to agree exactly, and each instruction's cycle cost except where
XRoar is named as differing from silicon (`KNOWN_CYCLES`: its native mode misses several
one-cycle savings, `TST`'s dead cycles, `MULD`'s sign cycles). `cov6309.py` reports what
ran: **every encoding and every indexed postbyte, in both modes**, with IRQ, FIRQ and NMI
through `CWAI`, `SYNC` and `ANDCC`, and undefined opcodes through the trap.

⚠ **What the differential cannot test, and why**: a state where XRoar is known to be wrong
cannot be compared past, so the generator never makes one (`DAA`'s 6309 correction, `LDQ`
with V set, `MULD`'s D = 0 flags - the last allowed for exactly one boundary); and where
nobody has asked silicon the core follows the addendum and the differential stays out
(**the seven undefined postbytes trap**; **a doubled prefix traps after two bytes**).

⚠ **Interrupt sampling is the datasheet's, not `mc6809i.v`'s**: a line counts if it is up
by the start of the instruction's last cycle, where `cpu6809.c` needs it a cycle sooner.
The core puts a write as soon as its address is known rather than after the dead cycles,
so the differential's interrupt port lands its changes at the next boundary - which cycle
of an instruction its write falls in is a bus-timing question the firmware will answer.

`make -C hardware/cpu sim` runs all of it (`SEEDS6309`, 16 by default).

### 4.2 Give it an oracle — four candidates, ranked

| | what it is | verdict |
|---|---|---|
| 1 | ⭐⭐ **NitrOS-9's own `IFNE H6309` paths** — hand-written 6309 assembly that has run on real Hitachi silicon for twenty years, exercising `TFM`, `LDW`/`STW`, native mode and the wide registers in the kernel's hottest routines | ⭐ **the strongest gate available, and it costs nothing to build.** `SCENARIOS=nitros9` (19 claims), `run-sdboot.sh` (45 claims, three card states, each rebooted through the POST) and `run-v3files.sh` (65 claims, the listing read off the pixels) already assert a booting, working system end to end. **Flip `H6309=1` and they become a 6309 conformance suite.** ⛔ But end-to-end: it says *something* is wrong, not which opcode |
| 2 | ⭐ **`reference/manuals/The 6309 Book (Burke & Burke).pdf`**, appendix A — the per-opcode cycle counts, with the native-mode column | ⭐ **this is `cycles.py`'s input.** That script already fails on any length that is not the datasheet's; point the same machinery at the book's table and the cycle half is closed statically, with no second implementation at all. ⚠ Transcribing an appendix is itself a source of error — it wants a check that the table is self-consistent (e.g. against the opcode map's own totals) |
| 3 | ⭐ **MAME's `hd6309` core** — a mature, independently written, widely exercised HD6309 implementation | ⭐ the right shape for a **differential oracle**, and it is exactly the pattern this repository already uses twice: `check:oracle` runs the audio card against an independent Paula, `check:modplay` A/Bs against libopenmpt. ⚠ **Licensing has to be looked at before a line of it is copied** — the honest use is as a *separate executable* producing a trace to diff against, never as source merged into `cpu6809.c`. ⚠ And it is a model of *silicon*, where `cpu6809.c` is a model of *a Verilog core*: where they differ, the 6309 half has no incumbent to defer to and the book decides |
| 4 | ⭐ **A real HD63C09E**, in a CoCo 3 or on the `hardware/cpu/` board | ⭐ `hardware/cpu/docs/plan.md` §6.1 already calls this *"best"*, and it is. ⛔ Slowest to arrange, and it is the thing the firmware is ultimately validated against rather than the thing that unblocks the software now |

⭐ **Take 2 and 3 together and reuse `gen.py`.** The exerciser's whole design —
self-contained chunks, every dependency loaded, control-flow chunks that arrange
their own targets so a divergence cannot run off into data, the first differing
trace line naming the guilty instruction — is exactly what a 6309 needs, and it
is agnostic about what sits on the other side of the diff. Extend its chunk
tables with the 6309 encodings and swap `mc6809e.v` for the oracle.

### 4.3 ⭐ BUILT 2026-09-21 — the build cannot be half-6309 any more

`recipes/arm6309/arm6309.mak` had `CPU ?= 6809` and nothing else; turning the
6309 on meant setting **two** variables that nothing checked against each other.

⛔ **`CPU=6309` alone links `libnos96309l2.a` and compiles every `ifne H6309`
path OUT** — `rules.mak`'s `--pragma=condundefzero` makes an undefined `H6309`
evaluate to zero — so you get the 6309 library, none of the 6309 code, and no
diagnostic. Every other recipe in the tree has the same shape (`coco3_6309.mak`
sets `CPU ?= 6309` on line 2 and `AFLAGS += -DH6309=1` on line 9).

Now: **`CPU=6309` implies `-DH6309=1`**, `CPU=6809` implies `-DH6309=0`, and
anything else is `$(error)` rather than a quiet fall-through to the 6809 branch.
⭐ **`CPU ?= 6309` is the default since 2026-09-24** (§4.4); `CPU=6809` is kept for
the Verilator benches, whose core is a 6809 (§4.5).

### 4.4 ⭐ BUILT 2026-09-24 — the build is `CPU=6309` and runs in native mode

NitrOS-9 builds `CPU=6309` by default and `rel_arm6309.asm` sets native mode
(`ldmd #$01`, with `D.MDREG` to match) before the kernel runs. The host emulator
runs `hd6309.c`, so every bench that boots NitrOS-9 on it runs this build.

⛔ **There is no "`H6309=1` with native mode off".** An `H6309` kernel's register
frames carry `E` and `F` (`os9.d`'s `R$` offsets), which only native mode's `SWI2`
and interrupts push. In emulation mode every system call's frame is two bytes
short, and the first one returned through the wrong address. Native mode is therefore part of the `H6309` build, not a later step.

What native mode required of the port:

| | |
|---|---|
| `krn.asm`'s `ArmFIRQ` | `pshsw`/`pulsw` under `H6309`. A native `FIRQ` stacks only `PC` and `CC` (`MD` b1 is 0, §5.3), and the handler uses `W` |
| `armio.asm`'s `Flip` | CoArm's hand-built entry frame stacks `E` and `F` between `DP` and `B`. A 6809-layout frame gave CoArm a `PC` made of `X` and `Y` |
| `armio.asm`'s `WrBlk` | `TFM` under `H6309`, with the 6809 loop kept |
| `rbsd.asm` | its `TFM` block read, already under `ifne H6309` |
| `software/emu/machine.c` | ⛔ **`SDDATA` is timed by the bus cycle, not by the instruction.** A `TFM` reads the port 32 times in one step; timed by the step, every read after the first was dropped and LSN 0 came back empty |

⭐ **The rule for 6309 code in the port** (`armio.asm`, above `WrBlk`) — it is
allowed on three conditions:

1. it is inside `IFNE H6309` **with a 6809 fallback**, because the Verilator
   benches build `CPU=6809` (§4.5);
2. it is **run** by a bench — a 6309 path nothing executes is not tested;
3. anything that builds a register frame by hand stacks `E` and `F`.

⭐ **Gates, on the native build:** `run-emu.sh` 28/28, sdtest 55/55,
`run-sdboot.sh` 46/46, `run-pcs.sh` (all legs, and the three mutations fail),
`run-v3move.sh` 24/24, `run-v3desk.sh` 48/48.

What is left is hand-written 6309 in our own modules: `vidcore`'s streams,
`vidcpy3`'s register sequences, `tbox`'s `GRow`, and `pcs` (§6 step 6).

### 4.5 The Verilog core — not required

⭐ **Decided 2026-09-24: `hd6309.c` is the specification, and no 6309 Verilog core
is planned.** The machine's CPU is STM32 firmware emulating an HD6309E, so what
has to be matched is the firmware. What it needs from a model is each
instruction's cycle count and the cycle each real read and write falls in, and
the C model has both (§4.1).

⚠ **`machine3.v` keeps `mc6809e`**, so `check:machine` and `v3machine_tb` run
`boot.asm` as 6809 code, and `run-machine.sh` builds NitrOS-9 **`CPU=6809`** for
`SCENARIOS=nitros9` and `reboot`. The boot ROM has no reason to be 6309. But it
has to be **said**: "146 claims, 0 failed" covers the 6809 build, and the
native build is covered by the host-emulator benches in §4.4. If a Verilog
core is ever written, `hardware/cpu/sim/test/run.sh` is the harness that will
validate it against `hd6309.c`.

## 5. ⚠ Hazards specific to this machine

### 5.1 ⛔ `TFM`'s interrupt and resume behaviour — the one instruction whose semantics this project must DECIDE

`docs/machine.md` §6 records it, and the wording matters: *"Settle `TFM`'s
interrupt/resume behaviour from silicon — and note it is a **choice**, not a
discovery, because this machine's 6309 is the project's own firmware. **Two cards
wait on it**"*.

#### 5.1.1 ⭐ The primary source is in `reference/`, and it says more than the repository thinks

⛔ **`sdcard.md`'s confidence table rates this "community documentation, not
silicon" and §14 says *"Neither is in `reference/`"*.** Both statements
understate the provenance. **Appendix 3-139 of `reference/manuals/The 6309 Book
(Burke & Burke).pdf` — which is in `reference/` — states the rule outright**, in
the `TFM` instruction reference:

> **Comments:** Each incremented or decremented register changes by W. W is
> cleared at the end of the instruction. **The instruction is interruptible. An
> interrupt during Form 4 re-reads the peripheral referenced by r1 without
> storing the previous data byte, advancing r2, or decrementing W; use Form 4
> only with interrupts disabled.**

And the four forms, from the same page:

| form | encoding | shape | who uses it here |
|---|---|---|---|
| 1 | `$1138` | `TFM r1+,r2+` — forward block move | net RX drain, serial FIFO drain, `F$Move` |
| 2 | `$1139` | `TFM r1-,r2-` — backward block move | — |
| 3 | `$113A` | `TFM r1+,r2` — **output to a peripheral** | ⚠ the SD **write** path, the audio sample upload, a future `TFM`→`VDATA` |
| 4 | `$113B` | `TFM r1,r2+` — **input from a peripheral** | ⛔ the SD **read** path |

⭐ **Three things follow that the repository does not currently say:**

1. **The documented hazard is Form 4 ONLY, and it is more specific than "re-reads
   the source".** The book names exactly what does not happen: the byte is not
   stored, `r2` does not advance, `W` does not decrement. `sdcard.md` §4.1's
   one-byte-cache framing is a reasonable reading of the same fact, and the
   consequence is identical — but the book is describing the *instruction's*
   observable state, not an internal cache, and it is the stronger citation.
2. ⛔ **The book is SILENT on Form 3**, which is the SD write path and the audio
   upload. So `sdcard.md` §9.2's *"can the destination be written twice?"* is
   genuinely unanswered — **and now we know it is unanswered by the best document
   we hold**, not merely un-looked-up. §12 step 1's three capture questions reduce
   to two that need silicon; question (a) has a documented answer.
3. ⭐ **`TFM` is `6+3W` cycles in BOTH modes** (Appendix A, `$1138`–`$113B`), so
   **native mode does not make it faster.** Every throughput figure that rests on
   it — `sdcard.md`'s 537 / 681 KiB/s, `net.md`'s 56 % of the wire, the 3.01
   cycles a byte — is mode-independent. That is worth knowing before §5.2's
   re-derivation, because it is the one constant native mode leaves alone.

⚠ **And one clause of `machine.md` §6 is stale**: *"the second one cannot retry a
lost frame"* describes the **port-era** net card. `net.md` §3.2 is now titled
*"…and why this card does not have one"* — net's ring is memory, and the
lost-frame argument survives only in `hardware/storage/docs/history.md`. **One card waits
on this, not two** — storage — with audio's sample upload behind it.

#### 5.1.2 Why a port breaks and RAM does not

`SDDATA` is a prefetch pipeline (`sdcard.md` §3.1): *"Reading `SDDATA` does two
things at once: it puts the byte from the **previous** burst on the data bus, and
it starts the burst that fetches the **next** one."* There is no address and no
index — the pointer into the block **is the count of reads performed**.

So a re-read is not idempotent; it is a `pop`. The block shifts by one from the
interruption point, ⛔ **and nothing detects it**: there is no error bit, and the
two CRC bytes are read at the wrong offset, so *"a block shifted by one shifts its
CRC with it"* (`rbsd.asm`). `sdcard.md` §4.2 prices the exposure at **0.15
expected hits per block — roughly one block in seven** against the machine's
~200 interrupts a second.

⛔ **And hardware cannot fix it** (`sdcard.md` §4.3): *"A `TFM` resume read and a
legitimate next read are the same bus cycle. The card cannot tell them apart."*

#### 5.1.3 The candidates, and what each costs

Today's answer is **E**, and it is correct under every outcome — this table is
about what the 21 % buys and what it costs.

| | behaviour | SD read | masking still needed | fidelity | ⭐ pro | ⛔ con |
|---|---|---|---|---|---|---|
| **A** | **Match silicon**, whatever a capture says | 537 KiB/s | yes — SD both paths, audio upload | ✅ exact | The CoCo 3 drop-in SKU is unarguable; `plan.md` Phase 5's exit criterion already says *"discrepancies resolved in favour of silicon"* | Keeps a 21 % tax and a 49 µs masked window ×16 a block, for a defect the machine never wanted. ⚠ And it is **not yet a known behaviour** for Form 3 |
| **B** | Silicon turns out **not** to re-read | 680 KiB/s | none | ✅ exact | Free | ⛔ **Not a choice** — an outcome, and the book says it is the unlikely one |
| **C** | ⭐ **Complete the byte, then take the interrupt** — store, advance `r2`, decrement `W`, *then* honour the request. Nothing is ever cached across an interrupt | **680 KiB/s** | ⭐ **none, anywhere in the machine** | ⚠ one ledger entry | **Zero firmware cycles** — a boundary condition in the state machine, not extra work. Latency cost is at most **one byte, 3 cycles**. Fixes Form 3 and Form 4 *by construction*, so audio's upload and a future `TFM`→`VDATA` are safe without anyone deciding again | Diverges from silicon. ⚠ Needs a mode bit and ~10 bytes of driver to keep the compatible path |
| **D** | **Uninterruptible `TFM`** | 680 KiB/s | none | ⛔ worse | Simplest to state | ⛔ **A 512-byte `TFM` is a 735 µs interrupt blackout.** `machine.md` §4's budget is 49 µs. Fatal to the VBL tick and the audio `/FIRQ`. **C dominates it completely** — same benefit, 3 cycles of latency instead of 735 µs |
| **E** | ⭐ **Status quo — chunk and mask** | 537 KiB/s | yes | ✅ exact | **Correct under every outcome**, which is why it is specified. Costs no decision | 21 %, and 16 masked windows a block on both paths |
| **F** | Card-side block buffer | 680 KiB/s | none on that card | ✅ exact | Removes the side-effecting port instead of the instruction | ⛔ **Rejected 2026-09-20**: 8 ICs → 16, plus a 64 KB physical region. *"A 16-IC card for 21 %."* |

#### 5.1.4 ⭐ The argument that is not in the documents: C's divergence is safe inward and risky outward

The objection to **C** is fidelity, and it is worth stating precisely rather than
as a feeling.

⭐ **C cannot break any program that is correct on real silicon.** The book's own
instruction is *"use Form 4 only with interrupts disabled"* — so a correct program
already masks, and a masked `TFM` never reaches the divergent path. **C only ever
changes the behaviour of a program that is already broken on a real 6309.** The
divergence is a strict superset of correct behaviour, in the same way that a CPU
which refused to lose data would be.

⛔ **The risk runs the other way.** Code written *here*, against C, may omit the
masking and then be wrong on real silicon — `sdcard.md` §11.6 makes exactly this
point about keeping the masked loop in the driver. That is an **outbound**
portability risk, and it is real, and it is managed by the mode bit rather than by
refusing C.

⚠ **And the CoCo 3 drop-in argument is weaker than it reads.** `sdcard.md` says C
must be off on that SKU because its value is being indistinguishable from the part
it replaces. But the same document observes that *"no CoCo software can [arrange
this], because a CoCo has no such port"* — so on a stock CoCo 3, C is
**unobservable**. ⚠ That is a judgement and not a proof: a third-party cartridge
could present a side-effecting port. The mode bit is worth having; the *fidelity
cost* on that SKU is, as far as anything known, zero.

⛔ **One thing to fix before deciding**: `hardware/cpu/docs/plan.md`'s Phase 5 exit
criterion — *"discrepancies resolved in favour of silicon"* — **forecloses C
without saying so.** If C is live, that criterion needs an explicit carve-out, or
the decision will be made by a checklist nobody re-read.

#### 5.1.5 ⭐⭐ WHAT NITROS-9 ITSELF DOES — 126 `TFM` sites, and one eyewitness

Asked 2026-09-21: *NitrOS-9 is heavily optimised for the 6309, including `TFM` —
what does its own use of the instruction tell us?* A great deal, because it is
twenty years of 6309 code that ran on real Hitachi silicon.

⚠ **`level2/arm6309/modules/rbsd.asm` is excluded from every count below.** It is
this project's own driver and its comments already cite `sdcard.md` §4.4; counting
it would launder our hypothesis back as corroboration.

**The census**, by form (126 sites):

| form | fixed operand | sites | masked? |
|---|---|---|---|
| 1 `r+,r+` / 2 `r-,r-` | none | **80** | ⭐ **never** — including `grfdrv.asm:1919`'s `tfm y+,u+` writing 16 bytes straight into **the GIME's palette registers** |
| 4 `r,r+`, fixed source is **RAM** (the memset idiom) | a constant byte | **34** | never, and never needs to be |
| 4 `r,r+`, fixed source is **a port** | the port | **9** | ⛔ **9 of 9 masked**, in three independent drivers |
| 3 `r+,r`, fixed destination is **a port** | the port | **4** | ⛔ **1 masked, 3 not** |

⭐ **The rule the authors were following is exact: the danger is a FIXED operand
that is a port, because a fixed operand is what a resume re-touches.** Forms 1 and
2 re-touch nothing fixed, which is why writing to the GIME with one is safe
unmasked and nobody ever thought about it.

##### The eyewitness — `level1/modules/rb1773.asm:547-551`

⭐⭐ **The single most valuable line in either repository on this question**, and
it is a contemporaneous observation, not a citation:

> ```
> * Don't use tfm if no halt important else need orcc #$50 for tfm
> * If an interrupt occurs during a tfm transfer, the SCII counter
> * will update but the tfm will repeat a byte and lose track.
> * If orcc #$50 used, then key presses may be lost even with no-halt
> * mode.
> ```

Three things come out of it:

1. ⭐ **"the tfm will repeat a byte and lose track"** — the Form 4 source re-read
   hazard, described from *observed behaviour on silicon*, in the operating system
   this machine boots. It independently confirms Appendix 3-139. `sdcard.md`'s
   confidence table calls the rule *"community documentation, not silicon"*; this
   is a practitioner reporting the failure.
2. ⛔ **The fix chosen was to ABANDON `TFM`, not to mask it.** The `ldw #256` and
   `ldy #RW.DAT` immediately above the comment are **vestigial `TFM` operands** —
   the instruction was replaced in place by `lda ,y / sta ,x+ / decw / bne`, which
   is the 6309 spelling of what `TFM` would have done, one indivisible pair at a
   time.
3. ⭐⭐ **And the reason masking was rejected is LATENCY, not doubt**: *"key
   presses may be lost."* They agreed the mask would fix it and could not afford
   512 bytes of it on a floppy driver sharing the CPU with the keyboard poller.

##### ⛔ The Form 3 question is NOT answered, and an earlier reading of mine said it was

`archive/drivers/tccc/tccchd.asm` is a **controlled experiment in one file, by one
author, against one controller**:

| | | |
|---|---|---|
| the **read** path (Form 4, port source) | `:920-947` | ⭐ **masked**, and 1024 bytes split into **four separate masked 256-byte `TFM`s** — chunking to bound latency, exactly `sdcard.md` §4.4's discipline, arrived at independently |
| the **write** path (Form 3, port destination) | `:686-704` | ⛔ **not masked at all** — a bare 1024-byte `tfm x+,u` into a SCSI write FIFO with IRQ and FIRQ live |

⛔ **So the tree is split 1–3 on Form 3**: `llscsi.asm:637` masks its write,
`tccchd.asm` does not, and neither author wrote down a reason. ⚠ A third site,
`tccchd.asm:1343-1353`, was *written masked and then commented out* in favour of a
byte loop.

⛔ **An interim reading of this evidence claimed "NitrOS-9 has masked exactly the
Form 3 case since 6309 support was written." That is wrong** — it generalised from
`llscsi` before `tccchd` had been looked at. `rbsd.asm`'s own comment — *"nothing
has established that an interrupted `TFM` cannot write its destination twice"* —
**stands, and the upstream tree does not relieve it.** What the tree shows is that
the authors distinguished the two directions and only defended the source side.

##### ⚠ Two things that are NOT evidence, and read like it

- **`F$Move` is masked, and not because of `TFM`.** `fmove.asm:102-108` wraps
  `tfm x+,u+` in `orcc #IntMasks`, ⛔ **but the 6809 branch masks too** and the
  file header says why: the routine has foreign DAT blocks swapped into MMU slots
  and the address space is temporarily lying. MMU, not `TFM`. The 256-byte cap is
  a DAT block, not a latency budget.
- **`llscsi`'s own comment attributes its mask to the wrong thing.** *"we have to
  mask interrupts for Level 1"* appears identically on the read and the write, and
  ⛔ **the 6809 branch of both — which is what would actually care about Level 1
  mapping — masks nothing**, across ~34 lines of unrolled `lda SCSIDATA,y`. The
  6809 path is *slower per byte*, so a controller-timing or a task-mapping
  explanation would demand the mask there more, not less. **The mask tracks the
  instruction; the comment does not.**

##### ⭐ A constraint on our firmware that nobody had written down

**`TFM` must leave `W` = 0 on completion, and five places depend on it.**
`cowin.asm:372-376` and `fvmodul.asm:451` use the post-`TFM` zero as a free
constant (`stw ,x   Save 0`); `grfdrv.asm:4888` hoists `clre` *outside* a loop and
reloads only `F`; and `rel.asm:400-415` trusts `E` to still be zero **across an
intervening `bsr`** — *"E=$00 already from TFM above"*.

⛔ **And nothing anywhere checks `W` after a `TFM` to detect a short transfer.**
There is no retry, no resume, no defence in depth. If a Form 4 against a port were
ever interrupted, the failure is exactly what `rb1773` describes — a byte repeated,
everything after it shifted — **and `W` is still zero, so nothing downstream
notices.**

##### ⭐⭐ What it does to the decision

Nothing here weakens **C**; two things strengthen it, and one narrows what it
claims.

1. ⭐ **C is unobservable to every `TFM` in NitrOS-9 that is correct today.** Every
   site is RAM↔RAM (where C and faithful silicon are identical) or masked (where
   they are identical because no interrupt arrives). C changes the behaviour of no
   working path.
2. ⭐⭐ **C is the feature the OS authors asked for and could not have.**
   `rb1773` gave up `TFM` — a 4× block move — because the only available fix cost
   more interrupt latency than a floppy driver could spend. C is that fix at
   **three cycles**, and it would hand `rb1773` its block move back.
3. ⚠ **C would also silently repair `tccchd`'s unmasked Form 3**, if the doubled
   write is real. That is a *benefit*, but note what it means: **C cannot be
   validated by "NitrOS-9 still boots"**, because the paths it changes are the
   ones nobody exercises under interrupts. `sdcard.md` §12 step 4's 10⁵ blocks
   with every interrupt running remains the only real gate.

⛔ **And the Form 3 capture is still owed.** The OS narrows it — the authors
plainly worried about the source side and plainly did not worry much about the
destination side — but "three drivers did not mask it" is not "it is safe", and
one of the four did.

#### 5.1.6 What to do, in order

1. ⭐ **Decide in `hardware/cpu/docs/plan.md`, not here and not in a model.** §4.3 currently
   says only *"specific state on interrupt/resume. Budget real time."* — it flags
   the work and not the rule.
2. ⭐ **The decision is not urgent, and it is now safe to defer**, because
   `cpu6809.c` **refuses `TFM`** (§4.0): nothing can accidentally be written
   against an undecided semantics. That was not true before — the core decoded
   `$1138` as a 2-cycle no-op and ran on.
3. **Then the capture**, which now owes two questions rather than three: can the
   **destination** be written twice (Form 3), and do dummy cycles drive `$FFFF`.
   ⭐ §5.1.5 narrows the first one but does not close it — the OS is split 1–3 on
   Form 3 and no author wrote down a reason.
4. **Then implement the decision in `cpu6809.c`**, and only then let `rbsd.asm`
   drop its masking — behind the mode bit, with the masked loop kept.
5. ⛔ **Under every option, `sdcard.md` §12 step 4 still applies**: 10⁵ blocks,
   byte-exact, **with video, audio, PS/2 and serial interrupts all running.** A
   test with interrupts off proves nothing here.

6. ⭐ **Whatever is chosen, `TFM` must leave `W` = 0 on completion** — five
   NitrOS-9 sites depend on it, one of them across a `bsr` (§5.1.5). That is a
   hard requirement on the firmware and on `cpu6809.c`, and it was not written
   down anywhere before today.

⭐⭐ **DECIDED 2026-09-21: C, with the mode bit, defaulting to the compatible
behaviour.** The specification is `hardware/cpu/docs/plan.md` §4.3.1 and §4.3.2; this
section is the argument that produced it and is kept as that. It is the only option that costs no silicon, no cycles and
no latency; its divergence cannot break software that was ever correct; and
⭐⭐ **it is the fix the OS authors wanted and could not afford** — `rb1773.asm`
gave up a 4× block move because the only available remedy cost more interrupt
latency than a floppy driver could spend, and C is that remedy at three cycles.

⚠ **What it does NOT do is settle Form 3.** C makes the question moot *for this
machine* by construction, which is a good reason to choose it and a bad reason to
skip the capture: the answer still matters for the CoCo 3 drop-in SKU, where the
compatible behaviour is what runs. What C costs is one ledger entry and the
discipline to keep the masked path in the driver — `sdcard.md` §11.6 prices that
at about ten bytes.

### 5.2 ⚠ Native mode moves the timing constants — re-derived 2026-09-24

The machine's software spaces its card accesses by **instruction count**, so
native mode's shorter instructions change the spacing. ⭐ **What it cannot change is
the E cycle**: two bus cycles are never closer than one E period, 476 ns at
2.0979 MHz, in either mode. A no-stall argument that rests on *consecutive E
cycles* (`docs/video-copyrect.md`'s *"476 ns apart, against a direct write's
≤318 ns of `SPANBUSY`"*) holds unchanged. What moves is every figure counted in
instructions.

Where native mode saves cycles in this port's loops: inherent ops (`DECB` 2 → 1),
the auto-increment postbytes (`,X+` 2 → 1), and the stack and return
instructions. Indexed-with-offset operands (`VR.VDATA,u`) and branches cost the
same in both modes. So the device loops, which are mostly those, barely move:

| loop | 6809 / emulation | native | what it has to stay above or below |
|---|---|---|---|
| `vidcore.asm`'s `Strm` copy (`lda ,x+` / `sta VR.VDATA,u` / `decb` / `bne`) | 16 cycles, 7.63 µs a byte | **14 cycles, 6.67 µs** | the 2.5 µs a direct, mask or sprite span takes to retire in cell mode — held |
| `Strm`'s fill loop | 10 cycles, 4.77 µs | **9 cycles, 4.29 µs** | the same 2.5 µs — held |
| `VcWait`'s `SPANBUSY` poll | 33 cycles a poll | **32** | a timeout far above the 40.7 µs worst span: `VcPolls` = 16,384 polls is **~250 ms** in either mode |
| `kbdarm.asm`'s `Send` (`ldx #60` hold, the `CLK` polls) | 8 cycles a pass | **8** | ps2.md §7's ≥ 100 µs inhibit: 60 passes are 229 µs — held |
| `TFM r+,r+` (`WrBlk`, `rbsd`'s block read) | — | 3 cycles, **1.43 µs a byte** | ≥ 318 ns between VRAM writes — held |

⭐ **Measured end to end, 2026-09-24: native mode is ~15 % faster at drawing
text.** `run-v3text.sh` was run twice on the same day: once as shipped, and once
with `CPU=6809 CPU6809=1` (the 6809 build on `cpu6809.c`). Both runs passed all
29 claims:

| `run-v3text.sh` | 6809 | native 6309 | |
|---|---|---|---|
| 40 characters, transparent (`v3t40`) | 369.60 ms | 318.54 ms | −13.8 % |
| 40 characters, composed opaque (`v3t40p`) | 222.94 ms | 190.18 ms | −14.7 % |
| 40 characters, out of the strike, build included (`v3t40s`) | 45.75 ms | 38.94 ms | −14.9 % |
| the strike's steady state (`v3tlow`) | 23.50 ms | 19.92 ms | −15.2 % |
| a call that draws nothing (`v3trct`) | 13.63 ms | 12.02 ms | −11.8 % |
| a stream copied to `/nil` — the OS's own cost | 0.727 s | 0.532 s | −27 % |

The OS gains most: a copy to `/nil` is nothing but RBF reading the card and
system calls, which is where the `IFNE H6309` paths and `rbsd`'s `TFM` are. The toolbox itself is still 6809 code (§6 step 6).

⛔ **Not re-derived yet:** `vidcpy3.asm`'s measured 129.7 µs IRQ-masked stretch,
and the figures `proportional-font.md` quotes. Each is a measurement, so it is
re-measured on the native build, not recomputed. §7 keeps the item open.

### 5.3 The smaller ones

- **6809 emulation mode is not bit-identical to a 6809.** The differences are few
  and documented, and `cpu6809.c` is currently matched to `mc6809i.v` rather than
  to an MC6809E anyway — so there are now *three* behaviours in play and the
  header has to say which one the file models.
- **The illegal-instruction trap at `$FFF0`.** `hardware/cpu/docs/plan.md` §2.4 flags it;
  ⚠ and `docs/machine.md:1146` notes the vectors are in ROM pointing at a fixed
  RAM jump table, so `$FFF0` needs a published slot in that table.
- **Divide-by-zero** takes the same trap and NitrOS-9 must survive it.
- **`MD` b1 (FIRQ stacks like IRQ)** interacts with the audio card's open-drain
  `/FIRQ` and `firqtst`. Leave it 0 and say so.
